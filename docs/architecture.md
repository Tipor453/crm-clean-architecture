# Подробное описание архитектуры

В данном проекте используется паттерн **Clean Architecture** (Чистая архитектура), предложенный Робертом Мартином. 

Главная идея этого паттерна — **разделение ответственности**. Код делится на независимые слои, чтобы бизнес-логика (правила работы компании) не зависела от базы данных, веб-фреймворков или интерфейса пользователя.

## 1. Главное правило (Правило зависимостей)

В Clean Architecture зависимости в коде должны быть направлены строго **внутрь**, к центру.
* Внешние слои (База данных) знают о внутренних (Бизнес-логика).
* Внутренние слои (Бизнес-логика) **ничего не знают** о внешних (Базе данных).

Если завтра мы решим перейти с базы данных PostgreSQL на MongoDB или вообще на файлы, мы не будем переписывать наши бизнес-правила. Мы просто напишем новый код для внешнего слоя.

## 2. Подробный разбор слоев

### 2.1. Слой Domain (Ядро)
Это самый независимый слой. Здесь лежат наши классы-сущности (`Client`, `Manager`, `Deal`, `Task`). 
* **Что здесь есть:** Только поля (данные) и простые методы, которые меняют состояние объекта (например, `Task::complete()` для отметки задачи выполненной).
* **Зависимости:** Ноль. Этот слой не импортирует ничего из других слоев.

### 2.2. Слой Application (Сценарии использования)
Этот слой описывает, *что именно* делает программа.
* **Сценарии (Use Cases):** Здесь лежат классы вроде `CloseDealUseCase`. Они управляют процессом: запрашивают данные, проверяют правила и вызывают методы у сущностей.
* **Интерфейсы (Контракты):** Здесь мы описываем интерфейсы репозиториев (например, `IDealRepository`). Мы говорим: «Нам неважно, как ты будешь искать сделку, но ты обязан иметь метод `getById()`». 
* **Зависимости:** Слой знает только о слое Domain.

### 2.3. Слой Infrastructure (Инфраструктура)
Этот слой отвечает за *сохранение данных* и общение с внешним миром.
* **Реализации (Adapters):** Здесь лежат классы вроде `InMemoryDealRepository`. Они реализуют (выполняют) те самые интерфейсы из слоя Application. 
* **Зависимости:** Этот слой зависит от Application (чтобы реализовать его интерфейсы) и от Domain (чтобы работать с сущностями).

## 3. Зачем мы так сделали? (Преимущества)

1. **Тестируемость:** Мы можем легко протестировать бизнес-логику (Use Cases), не подключаясь к реальной базе данных. Мы просто подсовываем сценарию фейковый репозиторий.
2. **Гибкость:** Если заказчик попросит добавить веб-интерфейс или мобильное приложение, мы просто добавим новый внешний слой, не трогая ядро.
3. **Порядок в коде:** Каждый разработчик в команде сразу понимает, где искать бизнес-правила, а где — код для работы с базой.

## 4. Как выглядит процесс (на примере закрытия сделки)

1. Менеджер нажимает кнопку «Закрыть сделку» в интерфейсе.
2. Контроллер перехватывает нажатие и вызывает `CloseDealUseCase`, передавая ему ID сделки.
3. Use Case обращается к интерфейсу `IDealRepository` с просьбой найти сделку.
4. Интерфейс перенаправляет запрос в `InMemoryDealRepository` (слой Infrastructure), который реально находит данные.
5. Use Case получает объект сделки (из слоя Domain) и вызывает у него метод `close()`.
6. Use Case просит репозиторий сохранить обновленную сделку.
